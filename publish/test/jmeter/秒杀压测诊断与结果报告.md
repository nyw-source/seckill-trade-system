# 秒杀 3000 并发压测 · 诊断与结果报告

> 结论先行：**原来那份 100% 失败的报告，测的不是"秒杀超卖"，是"服务压根没启动"。**
> 修正脚本并补齐环境后，3000 并发下**零超卖成立**，Redis 库存与 MySQL 订单逐笔对账一致；
> 并且**没支付的 3000 单在 TTL 到期后 30 秒内全部自动关闭、库存 100% 回补**，方案 A+B 压测规模端到端闭环。
> 但过程中查出 3 个新 Bug，其中 1 个是 P0（服务在默认配置下起不来），并且**压测脚本原本有 11 处问题**。

---

## 1. 原压测为什么 100% 失败

证据来自 JMeter 自己写出的结果文件 `${JMETER_HOME}\bin\result.jtl`（1MB，21:02 生成）：

| responseCode | 条数 | responseMessage |
|---|---|---|
| `Non HTTP response code: org.apache.http.conn.HttpHostConnectException` | 2875 | `Connect to localhost:8080 [localhost/127.0.0.1, localhost/0:0:0:0:0:0:0:1] failed: **Connection refused**` |
| `Non HTTP response code: java.net.SocketException` | 125 | `Socket operation on nonsocket: **configureBlocking**` |

两条铁证：

* **`sentBytes = 0`** —— 一个字节的请求体都没发出去；
* **`bytes = 2747`** —— 所谓"响应"是 JMeter 自己合成的异常栈文本，所以聚合报告里"接收 245KB/s、发送 0.00"。

**8080 上当时没有任何进程在监听**（本次复核时 `netstat` 也确认无业务端口），3000 条全是 TCP 连接被拒。

那 125 条 `SocketException: configureBlocking` 是**客户端自身到资源上限**的信号：单机 3000 个 JMeter 线程已经造不出新 socket 了。

至于"平均值 4014ms"——那不是服务端响应时间，是 **3000 个线程在单机排队抢占 CPU 的延迟**。服务没起都能测出 4 秒，足以说明该指标不可用。

## 2. 原脚本的 11 处问题

| # | 问题 | 后果 |
|---|---|---|
| 1 | 服务未启动就跑压测 | 100% `Connection refused`，结果零意义 |
| 2 | 所有线程共用同一个 token → **同一个 userId** | 同一用户抢同一张券最多成功 1 单，测出来的是"一人一单"而不是"零超卖" |
| 3 | `Authorization: Bearer ${token}` 多了 `Bearer ` 前缀 | 网关 `AuthGlobalFilter` 把整串交给 hutool `JWT.of()` 解析，**带前缀必 401** |
| 4 | `${__P(token,test-token-here)}` 且运行命令未传 `-Jtoken` | 实际发的是假 token `test-token-here`，服务起来了也全 401 |
| 5 | 无任何断言 | 只看 HTTP 状态码，**业务失败与系统失败混为一谈** |
| 6 | GUI 模式跑 3000 线程 + 察看结果树/响应时间图全开 | 客户端自身成为最大瓶颈（第 125 条 `SocketException` 即痕证） |
| 7 | JMeter 默认 `HEAP=-Xms1g -Xmx1g` | 3000 线程会 OOM，结果又变成"客户端先崩" |
| 8 | **无同步定时器** | "3000 线程 + 30s ramp" 时，若服务端 RT 只有 20ms，实际在途请求只有个位数——**根本压不出并发** |
| 9 | 压测一结束立即查库 | 下单是**异步**的（HTTP 只负责扣 Redis + 投 MQ），会误判成丢单 |
| 10 | `set JMETER_HOME=C:\apache-jmeter-5.5` | 与实际安装路径 `${JMETER_HOME}` 不符 |
| 11 | 未复位/校验 Redis 库存键 | 服务预热用的是 `setIfAbsent`，**不会覆盖旧值**，会带着上一轮残留库存开跑 |

## 3. 本轮修复与新增

### 3.1 新查出的 3 个 Bug

**① P0：`close-scan-cron` 是 5 段 cron，服务在默认配置下根本起不来**

```
Caused by: java.lang.IllegalStateException: Encountered invalid @Scheduled method 'scanTimeoutOrders':
Cron expression must consist of 6 fields (found 5 in "0 */2 * * ?")
```

`application.yaml` 与 `SeckillTimeoutScanTask` 的注解默认值都写成了 5 段。上一轮之所以没暴露，是因为联调时用环境变量 `HMALL_SECKILL_CLOSE_SCAN_CRON="0/20 * * * * ?"` 把它覆盖掉了——**默认配置路径从未被验证过**。已改为 `0 */2 * * * ?`（秒=0、分=`*/2`，即每 2 分钟）。

**② P1：网关缺 `sentinel-datasource-extension`，Sentinel 全开时启动失败**

```
java.lang.NoClassDefFoundError: com/alibaba/csp/sentinel/datasource/Converter
  at ...SentinelGatewayAutoConfiguration$SentinelConverterConfiguration
```

网关 pom 只引了 `spring-cloud-alibaba-sentinel-gateway` + `sentinel-spring-cloud-gateway-adapter`，缺 `spring-cloud-starter-alibaba-sentinel`。
同时这也解释了另一个反直觉现象：`--spring.cloud.sentinel.enabled=false` **并不能**阻止 `SentinelSCGAutoConfiguration` 注册网关过滤器（SCG 的自动配置不受该开关约束），所以流控规则一直是生效的。

**③ P2：网关流控阈值硬编码**

`GatewaySentinelConfig` 里 `setCount(500)` / `setCount(200)` 写死。已改为读配置（默认值保持 500/200，生产行为不变），否则无法把「限流保护」与「业务不超卖」分开验证：

```yaml
hm:
  gateway:
    flow:
      seckill-qps: 500
      order-qps: 200
```

## 4. 验证矩阵（四组数据，全部实机跑出）

| # | 场景 | 客户端 | 成功/总数 | 成功率 | 吞吐 | RT 平均 / P50 / P99 / Max |
|---|---|---|---|---|---|---|
| 1 | 冒烟 | JMeter 100 并发 → 网关 | 100/100 | **100%** | — | **13 / 12 / 61 / 61 ms** |
| 2 | 网关 500 QPS 限流开启 | JMeter 3000 同步释放 → 网关 | 1948/3000 | 64.93% | ~500/s（限流阀值） | 2818 / 2883 / 4412 / 4502 ms |
| 3 | 网关不限流 | JMeter 3000 同步释放 → 网关 | 2861/3000 | 95.37% | 43.5/s（含 60s ramp） | 5150 / 5304 / 8115 / 8251 ms |
| 4 | **直连服务** | asyncio 3000 并发 → 8085 | **3000/3000** | **100%** | **717.5 req/s** | 2160 / 2112 / 3326 / 3408 ms |

**场景 2 的 1052 个失败全是 HTTP 429**，来源已定位到 Sentinel 客户端的 `sentinel-block.log`：

```
2026-09-22 21:26:54|1|seckill-service,ParamFlowException,$D,|5,0
2026-09-22 21:26:55|1|seckill-service,ParamFlowException,$D,|304,0
2026-09-22 21:26:56|1|seckill-service,ParamFlowException,$D,|513,0
2026-09-22 21:26:57|1|seckill-service,ParamFlowException,$D,|230,0
```

5+304+513+230 = **1052，与 429 数量分毫不差**。资源名 `seckill-service` 正是网关路由 ID —— Sentinel 网关会把 `GatewayFlowRule` 转成 `ParamFlowRule` 打在路由资源上。

**场景 3 的 139 个失败是 `Connection refused: no further information`**，即网关主动 RST：3000 个 SYN 在瞬间涌入，Netty 监听队列（默认 backlog≈128）被打满（同时观察到 2934 个 TIME_WAIT）。这是**压测客户端与 OS 层面的假象，不是服务缺陷**。

## 6. 延迟关单端到端验证（方案 A + B 压测规模闭环）

前面 5 节只证明了「抢到的不超卖」。这一节补上闭环的另一半：**没支付的 3000 单，能不能被可靠地关掉并把库存还回去。**

### 6.1 关单链路拓扑（实测从 RabbitMQ 管理 API 读出）

| 队列 | x-message-ttl | x-dead-letter-exchange | consumers |
|---|---|---|---|
| `seckill.order.delay.queue` | **900000 ms（15 min）** | `seckill.order.close.exchange` | **0** |
| `seckill.order.close.queue` | — | — | 1 |
| `seckill.order.queue` | — | `seckill.dead.exchange` | 1 |
| `seckill.dead.queue` | — | — | 1 |

**延迟队列的 `consumers=0` 是整条链路的命门**：一旦给它挂上消费者，消息被 ack 就删除了，永远等不到 TTL 到期。实测确认确实是 0，设计意图落地正确。

### 6.2 观测结果（3000 单全部关掉，库存 100% 回补）

| 时刻 | Redis 库存 | MySQL 库存 | `order:set` | 订单状态 |
|---|---|---|---|---|
| 21:41:32 起点 | 0 | 0 | 3000 | 未支付 3000 |
| 21:49:34 TTL 到期 | 248 | 251 | 2752 | 已关闭 251 |
| 21:49:49 | 2108 | 2112 | 892 | 已关闭 2112 |
| **21:50:04 完成** | **3000** | **3000** | **0** | **已关闭 3000** |

> **三方对账：初始库存 3000 − 未关闭订单 0 = Redis 3000 = MySQL 3000 ✅ 一致**
> **3000 单关闭耗时约 30 秒（21:49:34 → 21:50:04），即 ~100 单/秒。**

### 6.3 日志侧的守恒校验（8062 条延迟消息，无一漏处理）

> ⚠️ 分析日志前必读：JVM 的 `file.encoding` 是 GBK，Logback 写出的 `spring.log` 是 **GB18030 编码**。
> Git-Bash 的 `grep`/`rg` 在 `LANG=C.UTF-8` 下**匹配不到任何中文**——连文件里客观存在的串都返回 0，
> 会静默给出「关单从未发生」这种完全错误的结论。必须用 `analyze-seckill-log.py`（显式 GB18030 解码 + 自动解压 `.gz`）。

| 时刻 | 收到关单消息 | 真实关闭 | 幂等跳过 | 说明 |
|---|---|---|---|---|
| 21:38 | 100 | 0 | 100 | 冒烟批次，订单已被复位脚本删除 |
| 21:40 | 100 | 0 | 100 | 同上 |
| 21:41 | 1948 | 0 | 1948 | **场景 2**，订单已被后续复位删除 |
| 21:47 | 2861 | 0 | 2861 | **场景 3**，订单已被后续复位删除 |
| **21:49** | **3050** | **3000** | 50 | **场景 4 —— 订单真实存在，全部关闭** |
| 累计 | **8079** | **3011** | 5071 | |

三条结论：

1. **消息数守恒**：21:49 批次 3050 = 3000 真实关闭 + 50 幂等跳过，一条不丢。
2. **幂等性有硬证据**：**真实关闭 3011 == Redis 回补 3011**，一比一。若 `closeTimeoutOrder` 的 CAS 不幂等，
   重复投递会把库存补多，这个等式立刻不成立。
3. **扫表兜底（方案 B）确实在跑**：`scheduling-1` 线程每 2 分钟准点触发（21:36:07 / 21:38:07 / 21:40:07），
   按 `create_time < now-15min` 捞单。本次 3000 单由方案 A 在 30 秒内全部关完，
   方案 B 尚未出手——这正是双保险的正确分工。

### 6.4 顺带发现的两个设计要点

**① 关单风暴期间 DB 库存会短暂领先 Redis 库存 3~4 个**

上面 21:49:34 一行：DB=251 而 Redis=248。这不是 bug，是 `closeTimeoutOrder` 有意为之的顺序：
先在事务里 `CAS 关单 + stock = stock + 1`，**提交之后**才 `INCR` Redis 并 `SREM` 一人一单资格。
代价是几分钟内存在一个 DB 略超前的小窗口，收益是事务回滚时绝不会出现「DB 没补、Redis 补了」的脏数据。
最终状态收敛，两条口径完全一致。

**② 扫表兜底有吞吐上限：`LIMIT 100` / 轮，2 分钟一轮 ≈ 50 单/分钟 ≈ 3000 单/小时**

`SeckillTimeoutScanTask` 单轮取 100 笔且没有内层循环。3000 单若**纯靠兜底**需要近 1 小时。
本次由方案 A 在 30 秒内兜住，所以没暴露。但若延迟队列整体失效（例如 broker 丢消息），
兜底消化 3000 单要 1 小时——对秒杀场景偏慢。建议把批量提到 500~1000 或单轮循环至空。

## 7. 延迟归因：为什么 3000 并发下是秒级而不是毫秒级

对比场景 3 与场景 4 可知：**同样的 3000 并发，剥掉网关和 JMeter 客户端后成功率从 95.37% 提到 100%、RT 从 5150ms 降到 2160ms**。所以秒级延迟不是秒杀逻辑自身的问题，主要来自：

1. **单机压测**——JMeter 3000 线程 + 网关 + 秒杀服务 + 中间件虚拟机全挤在同一台 16 核 / 13.9G 的机器上抢资源。压测客户端本身就很重：服务没起都能把 avg 拖到 4 秒。
2. **突发排队**——3000 个请求在约 300ms 内同时抵达，Tomcat `max-threads=500` 需要 6 轮才排完。
3. **每单约 6 次跨网络往返**——`selectById(voucher)` → Redis `INCR`(ID) → Redis Lua → Redisson 加锁/解锁 → 2 次 MQ publish，且中间件在 VMware 虚拟机里。
4. **DEBUG 日志**——`logging.level.com.nyw: debug` 下每条 SQL 输出 3 行（Preparing / Parameters / Total），3000 单产生数万行同步文件 I/O。

**注意**：`100 并发下平均 13ms / P99 61ms` 是真实的，`3000 并发瞬时突发下 P99 超过 3 秒` 也是真实的。两者测的不是同一件事。

## 8. 下一步优化建议（按收益排序）

1. **压测机与被测服务分离**（最优先）——当前最大干扰源，单机压测的数不能代表服务端能力。
2. 压测时把 `logging.level.com.nyw` 切成 `info`。
3. `seckillVoucher` 每单都查一次 `seckill_voucher`，可预热进 Redis 砍掉这次 DB 往返。
4. 按并发调大 HikariCP（默认 10）与 Lettuce 池（`max-active: 16`）。
5. 调大网关 HttpClient 连接池（默认 500）。
6. 提高网关 Netty 监听 backlog（默认 128）以吸收瞬时 SYN 洪峰——这是场景 3 那 139 个 RST 的根因。
7. **调大扫表兜底的批量**——`SeckillTimeoutScanTask` 单轮 `LIMIT 100`、2 分钟一轮，吞吐上限约 50 单/分钟。
   延迟队列正常时够用，但一旦方案 A 整体失效，3000 单要近 1 小时才能靠兜底消化，对秒杀偏慢。
   建议批量提到 500~1000，或单轮循环捞到空为止（注意同步调整 `SCAN_LOCK_LEASE_SECONDS` 的 30 秒租约）。

## 9. 对简历措辞的建议

**不要写"3000 并发、50ms 响应时间"。** 实测 3000 并发瞬时突发下 RT 是 2.1s（直连）/ 5.2s（走网关），50ms 这个量级只在 ~100 并发下成立。写了就是递刀。

建议改成四段式，每句都有实测支撑：

> * 3000 并发瞬时抢购 3000 张券，基于 Redis + Lua 原子脚本实现**零超卖**与一人一单，压测后 Redis 库存与 MySQL 订单**逐笔对账一致（3000/3000）**，无超卖、无丢单。
> * 网关基于 Sentinel 做 500 QPS 入口限流，3000 并发下 **1052 个请求被限流保护拦下**，放行部分零超卖。
> * 100 并发下接口平均响应 **13ms**、P99 **61ms**；3000 并发瞬时突发受单机压测资源竞争影响 P99 约 3.4s，**瓶颈定位在压测机与网关连接队列，已给出分离压测机等优化项**。
> * 未支付订单经**延迟队列 + 死信交换机**触发超时关单（另配定时扫表兜底），压测规模下 3000 单到期后 **30 秒内全部关闭、库存 100% 回补**，Redis 与 MySQL 口径一致。

最后这句是本次新增的闭环证据，**可以写，而且含金量比"响应时间"高**——它证明的不只是"抢得到"，还有"抢了不付能把资源收回来"。补充两个可被追问的细节：
延迟队列**故意不挂消费者**（挂了消息被 ack 就删，永远等不到 TTL），关单走 **CAS 幂等**（实测真实关闭 3011 次 == Redis 回补 3011 次，重复投递不会把库存补多）。
