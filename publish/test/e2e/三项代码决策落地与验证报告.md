## 1. 决策①：CacheServiceImpl 补 Bean 启用（并真正接上商品查询）

### 1.1 根因修正

你给的两条判断都对，但实际有**三层**原因，只补 Bean 还不够：

1. **Spring Boot 只提供 `RedisTemplate<Object,Object>` 和 `StringRedisTemplate`**，确实不提供 `RedisTemplate<String,Object>` —— 所以构造函数注入直接找不到 Bean；
2. `@ConditionalOnBean` 写在被组件扫描的 `@Component` 上条件恒 false（组件扫描早于自动配置）；
3. **还有一层你没提到**：`CacheServiceImpl` 在 `com.nyw.common` 包下，而各服务的 `@SpringBootApplication` 默认只扫自己所在的包。只有 seckill-service / order-service 恰好写了 `scanBasePackages = "com.nyw"` 才能扫到，**item-service 这类服务永远拿不到这个 Bean**。

### 1.2 落地方式

| 文件 | 变更 |
|---|---|
| `nyw-common/config/RedisConfig.java`（新增） | 提供 `RedisTemplate<String,Object>`（String key + `GenericJackson2JsonRedisSerializer` value）。用 `@AutoConfigureBefore(RedisAutoConfiguration.class)` 保证顺序，用 `@ConditionalOnMissingBean` 让 Boot 的 `RedisTemplate<Object,Object>` 自动退让 |
| `nyw-common/cache/CacheAutoConfiguration.java`（新增） | 把 `CacheServiceImpl` 改成 `@Bean` 注册，**不再依赖组件扫描**，所有依赖 nyw-common 的服务行为一致 |
| `nyw-common/resources/META-INF/spring.factories` | 注册上面两个类（和项目原有 `MyBatisConfig`/`JsonConfig` 同一套风格） |
| `nyw-common/cache/impl/CacheServiceImpl.java` | 去掉 `@Component` 与 `@ConditionalOnBean`；**把读写路径改成真正使用注入进来的 `RedisTemplate`**（原来它只用 `StringRedisTemplate` 读写，注入的 `RedisTemplate` 是个完全没用上的字段） |
| `nyw-common/cache/CacheService.java` | 新增 `evict(prefix, id)`，用于 Cache-Aside 写路径失效 |

**一个必须说清楚的技术点**：`GenericJackson2JsonRedisSerializer` 默认的 ObjectMapper **不认识 `LocalDateTime`**，
而 `RedisData.expireTime` 就是 `LocalDateTime`，不注册 `JavaTimeModule` 会直接抛 `InvalidDefinitionException`。
所以 `RedisConfig` 里显式注册了 `JavaTimeModule` 并关掉 `WRITE_DATES_AS_TIMESTAMPS`，
同时在 nyw-common 补了 `jackson-datatype-jsr310` 依赖（版本由 spring-boot-parent 管理，2.13.5）。

### 1.3 接入商品查询（让简历那句话真的成立）

原来全项目**没有任何一处注入 `CacheService`**，"接入商品查询"是没有代码支撑的。本轮补上：

- `IItemService#queryItemById(Long)`：走 `cacheService.queryWithPassThrough(...)`，缓存未命中才回源；
- `ItemServiceImpl`：覆写 MyBatis-Plus 的 `updateById` / `removeById`，并在 `deductStock` 后统一 `evict` ——
  放在 Service 层而不是 Controller，是为了不漏掉任何调用方（`saveOrUpdate` 内部也会走 `updateById`）；
- `ItemController#queryItemById` 改为调用带缓存的方法。

### 1.4 验证结果（`test/e2e/verify-item-cache.py`，11/11 PASS）

手法：**不加埋点，直接数应用日志里真实执行的 SQL 条数**（MyBatis 会打印 `==> Parameters: <id>(Long)`）。

| 用例 | 断言 | 结果 |
|---|---|---|
| V1 首次查询 | 回源 SQL 恰好 1 条 | ✅ |
| V2 二次查询 | 0 条 SQL（缓存命中），且两次返回内容一致 | ✅ |
| V3 查不存在的商品 ×2 | 第 1 次 1 条 SQL、第 2 次 0 条（空值缓存挡住穿透） | ✅ |
| V4 更新商品后再查 | 更新前 0 条 → 更新后重新 1 条（缓存被失效） | ✅ |

> 这正好补上了上一轮因为 Nacos 9848/9849 封闭而**唯一没跑成**的那项验证（"缓存两次查询 SQL 条数对比"）。
> 现在不需要经过 Feign 也能验，因为被缓存的查询就在 item-service 自己身上。

## 2. 决策②：knife4j 升到 openapi3 4.4.0

### 2.1 你的前提有一处要更正（但结论仍然对）

**本项目是 Spring Boot 2.7.12 + JDK 11 + `javax.*`，不是 Spring Boot 3。**
所以不能用 `knife4j-openapi3-jakarta-spring-boot-starter`（那要 SB3 + `jakarta.*`，用了直接起不来），
必须用**非 jakarta** 的 `knife4j-openapi3-spring-boot-starter:4.4.0`（依赖 springdoc-openapi-ui 1.7.0）。

但**升级本身是必须的，而且比我原先以为的更要紧**：
旧依赖 `knife4j-openapi2-spring-boot-starter:4.1.0`（springfox 2.10.5）在 SB 2.6+ 上启动会 NPE，
上一轮是**靠额外排除 `Knife4jAutoConfiguration` 才能启动**的 —— 也就是说**接口文档功能一直是死的**。
升级后不再需要任何排除项（本轮的启动命令里已经完全没有 `--spring.autoconfigure.exclude`）。

### 2.2 落地方式

1. `nyw-common/pom.xml`：`knife4j-openapi2-spring-boot-starter:4.1.0` → `knife4j-openapi3-spring-boot-starter:4.4.0`；
2. 注解迁移：写了 `test/migrate_swagger.py` 批量处理，**25 个文件 / 217 处**，脚本自带残留检查，结果"无 springfox 残留"：

   | 旧 | 新 |
   |---|---|
   | `@Api(tags="x")` | `@Tag(name="x")` |
   | `@ApiOperation("x")` | `@Operation(summary="x")` |
   | `@ApiModelProperty("x")` | `@Schema(description="x")` |
   | `@ApiModelProperty(value="x", required=true)` | `@Schema(description="x", requiredMode = Schema.RequiredMode.REQUIRED)` |
   | `@ApiParam` / `@ApiImplicitParam(s)` | `@Parameter` / `@Parameters` |

3. `nyw-common/config/OpenApiConfig.java`（新增）：项目里**原本没有任何 `Docket` Bean 或 `@EnableSwagger2`**，所以没有东西可删；
   新增一个 springdoc 的 `OpenAPI` Bean，标题取 `spring.application.name`，于是 6 个服务各有各的文档抬头。

### 2.3 验证结果

```

                     "description":"秒杀交易系统微服务接口文档（springdoc-openapi3 + knife4j 4.4.0）",
```

## 3. 决策③：网关加兜底 + 堵越权洞

### 3.1 你担心的现象和真正的洞不是同一个位置（这点很关键）

原 `AuthGlobalFilter` 对**非白名单路径**其实是安全的：它解析 token 后用
`request.mutate().header("X-User-Id", ...)` 覆写请求头，而 `ServerHttpRequest.Builder#header` 是 **replace 语义**，
客户端伪造的值会被覆盖掉。

**真正漏的地方是白名单分支**：命中 `excludePaths` 时直接
`return chain.filter(exchange)`，**原请求头原封不动带下去了**。
而白名单里就有 `/items/**`、`/search/**`、`/users/login` ——
任何人发一个 `X-User-Id: 1` 请求 `/items/1`，下游服务就会把这个头当成本人身份。
这就是那条能撞上简历"拦截横向越权"的洞。

### 3.2 落地方式

`AuthGlobalFilter` 改成「**第一步就无条件摘头，再按解析结果重新写**」：

```
1. 无论走哪个分支，先 headers.remove("X-User-Id")
2. 带 token 且校验通过        → 用 token 里的 userId 覆写
3. 带 token 但校验失败：
   非白名单 → 401；白名单 → 按匿名放行（不注入身份）
4. 不带 token：
   调试开关开启且带了 X-User-Id → 透传（打 WARN 日志）
   白名单 → 放行（无身份）
   其余   → 401
```

`AuthProperties` 新增 `debugAllowUserHeader`（默认 **false**），
开关打开时启动日志会打印 5 行醒目的**安全告警**，避免误带到生产。

> 命名说明：你给的示例是 `hm.gateway.debug-allow-user-header`，
> 但网关已有的配置前缀就是 `hm.auth`，为保持一致实际落地为 **`hm.auth.debug-allow-user-header`**。

### 3.3 验证结果

手法：网关命令行临时挂一条指向本地回显服务的路由（不改任何 yaml），
回显服务把收到的身份头吐回来，于是"网关照不照抄客户端身份"变成可观测事实。
脚本：`test/e2e/verify-gateway-auth.py` + `test/e2e/echo-server.py`。

| A2 受保护路径 + 伪造身份头 + 无凭证 | 401 | ✅ |
| A3 受保护路径 + 伪造身份头 + 非法凭证 | 401 | ✅ |
| **A4 白名单路径 + 伪造身份头** | 200，且下游收到身份为 **null** | ✅ ★洞已堵 |
| A5 白名单路径 + 伪造身份头 + 非法凭证 | 200，且下游收到身份为 null | ✅ |

## 4. 额外发现：网关 2 个「启动即失败」P0

试着启动网关才发现——**网关同样从未成功启动过**（和上一轮 seckill-service 情况一样）。

### P0-5：Bean 名冲突，网关直接 `APPLICATION FAILED TO START`
```
The bean 'sentinelGatewayFilter', defined in class path resource
[com/alibaba/cloud/sentinel/gateway/scg/SentinelSCGAutoConfiguration.class],
could not be registered. A bean with that name has already been defined in
class path resource [com/nyw/gateway/config/GatewaySentinelConfig.class]
and overriding is disabled.
```
根因：`GatewaySentinelConfig` 手工 `new` 了 `SentinelGatewayFilter` 和
`SentinelGatewayBlockExceptionHandler`，而 Spring Cloud Alibaba 的
`SentinelSCGAutoConfiguration` 已经用 `@ConditionalOnMissingBean` 注册过这两个 Bean。
**修法**：删掉这两个重复 Bean，只保留自定义的 `BlockRequestHandler`（它是 `@ConditionalOnMissingBean`，会正常覆盖默认实现）和限流规则。
**没有**用 `spring.main.allow-bean-definition-overriding=true` 去掩盖。

### P0-6：`@RequiredArgsConstructor` 与手写构造器同时存在
修完 P0-5 后暴露出来：
```
Failed to instantiate [com.nyw.gateway.filter.AuthGlobalFilter]: No default constructor found
```
根因：类上挂了 Lombok `@RequiredArgsConstructor`（会生成 `(AuthProperties, JWTSigner)` 构造器），
同时又有手写构造器 → 多个构造器且都没 `@Autowired` → Spring 退回去找无参构造器，找不到就炸。
而且 Lombok 生成的构造器要注入 `JWTSigner`，那本来就不是 Bean。
**修法**：去掉 `@RequiredArgsConstructor`，保留手写构造器。

修完这两条后网关 9.593s 正常启动。

## 5. 方案 B 到底做没做：做了，而且两轮都有实测

你问的这个我可以直接回答：**方案 B 做了**，就是 `SeckillTimeoutScanTask`：

- `@Scheduled(cron = "${nyw.seckill.close-scan-cron:0 */2 * * ?}")`，默认每 2 分钟；
- 捞 `status=1 AND create_time < NOW() - order-timeout-minutes LIMIT 100`（复用 `SeckillOrderMapper#selectTimeoutOrders`）；
- 复用 `closeTimeoutOrder` 的 CAS 幂等，所以重复扫到同一单不会重复回补；
- Redisson 锁 `lock:mutex:seckill:close-scan`，双实例只有一个执行；
- `(status, create_time)` 联合索引已建。

**本轮回归证据**（`test/e2e/verify-seckill-e2e.py`，86.9s，全绿）：
- V2 延迟队列到期自动关单 → status=3、库存回补、一人一单释放；
- V4 同一条关单消息投 3 次 → 库存只 +1，日志「订单不存在或已处理，跳过关闭（幂等）」；
- V5 已支付订单收到关单消息 → status 仍 2、库存不回补；
- **V6 手工造一条"没人发关单消息"的超时单 → 被定时任务捞出并关闭、库存回补** ← 这就是方案 B 的直接证据；
- V7 日志关键字 4 条全命中；收尾把 DB/Redis 还原到压测前置状态。

被追问时可以直接答：间隔 2 分钟（可配）；用 `(status, create_time)` 联合索引避免全表扫；
重复扫到同一单靠 CAS `UPDATE ... WHERE id=? AND status=1` 影响行数为 0 直接跳过，天然幂等。
