## 2. 启动阻塞与修复

第一轮 6 个服务**全军覆没**，但其实是 5 个互不相干的原因。

### 🔴 P0-1　Nacos 没启动（VM 侧，未修）

**现象**：`cart-service`、`item-service` 直接 `APPLICATION FAILED TO START`

```
org.springframework.context.ApplicationContextException: Failed to start bean 'webServerStartStop'
Caused by: java.lang.reflect.UndeclaredThrowableException
	at com.alibaba.cloud.nacos.registry.NacosServiceRegistry.register(NacosServiceRegistry.java:82)
Caused by: Connection refused: /${MW_HOST}:9848
```

**根因**：`NacosServiceRegistry.register()` 在 `WebServerInitializedEvent` 阶段抛异常 → 冒泡成 `Failed to start bean 'webServerStartStop'` → 应用自杀。
**Nacos 是硬依赖，不是"可选组件"**。而且 Nacos 2.x 客户端注册走 gRPC **9848**（不是 8848）。

**实测端口**（本机 → VM）：

| 端口 | 状态 |
|---|---|
| 3306 MySQL / 6379 Redis / 5672+15672 RabbitMQ | ✅ OPEN |
| **8848 Nacos HTTP** | ❌ **CLOSED** |
| **9848 / 9849 Nacos gRPC** | ❌ CLOSED（一直没开过） |

**修复（在 VM 上执行，三选一）**：

```bash
# ① 先看容器什么状态
docker ps -a --format '{{.Names}}\t{{.Status}}\t{{.Ports}}'

# ② 如果只是停了
docker start nacos

# ③ 如果容器没有 9848/9849 端口映射，重建（数据在 nacos 库里，volume 照旧挂）
docker rm -f nacos
docker run -d --name nacos -p 8848:8848 -p 9848:9848 -p 9849:9849 \
  -e MODE=standalone nacos/nacos-server:v2.1.0-slim

# ④ 如果是防火墙
firewall-cmd --add-port=9848/tcp --add-port=9849/tcp --permanent && firewall-cmd --reload
```

本机验证：`Test-NetConnection ${MW_HOST} -Port 9848` 应为 True。

**本机临时绕开**（不带 Nacos 也能起，只是不会注册到注册中心）：

```
--spring.cloud.nacos.discovery.enabled=false
```

> ⚠️ 绕开之后网关**无法通过 `lb://service-name` 路由**到下游（服务没注册）。所以这条路只能用来验证"启动链路"，不能用来验业务。本次报告的第 3 节就是这么跑的。

### 🔴 P0-2　gateway 缺 `spring-cloud-starter-alibaba-sentinel`

**现象**：
```
Caused by: java.lang.NoClassDefFoundError: com/alibaba/csp/sentinel/datasource/Converter
Caused by: java.lang.ClassNotFoundException: com.alibaba.csp.sentinel.datasource.Converter
  at ...SentinelGatewayAutoConfiguration$SentinelConverterConfiguration$SentinelJsonConfiguration
```

**根因**：`gateway/pom.xml` 只引了 `spring-cloud-alibaba-sentinel-gateway` + `sentinel-spring-cloud-gateway-adapter`，**没引 `spring-cloud-starter-alibaba-sentinel`**，而 SCG 的自动配置需要它带来的 `sentinel-datasource-extension`。
实测：`gateway.jar` 的 `BOOT-INF/lib/` 里**只有 `spring-cloud-alibaba-sentinel-datasource`，没有任何 `sentinel-datasource-extension`**。

**修复** —— `gateway/pom.xml` 新增：
```xml
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-sentinel</artifactId>
</dependency>
```

**修复后验证**：`gateway.jar` 里出现 `sentinel-datasource-extension-1.8.5.jar` ✅

### 🔴 P0-3　order-service 缺 `sentinel-datasource-nacos`

**现象**：
```
Caused by: java.lang.NoClassDefFoundError: com/alibaba/csp/sentinel/datasource/nacos/NacosDataSource
BeanCreationException: Error creating bean with name 'ds1-sentinel-nacos-datasource'
```

**根因**：`order-service/application.yaml` 配了 `spring.cloud.sentinel.datasource.ds1.nacos`（从 Nacos 拉流控规则），
但 pom 里**只有 `spring-cloud-starter-alibaba-sentinel`，没有 `sentinel-datasource-nacos`** → 工厂类加载不出来。
（`seckill-service` 的 pom 里本来就有这个依赖，见 P0-4。）

**修复** —— `order-service/pom.xml` 新增：
```xml
<dependency>
    <groupId>com.alibaba.csp</groupId>
    <artifactId>sentinel-datasource-nacos</artifactId>
    <version>1.8.8</version>
</dependency>
```

**冲突检查**：`sentinel-datasource-nacos` 会传递 `nacos-client`（1.x），担心顶掉 2.x 客户端。
实测三方 `nacos-client` 均稳定解析为 **2.0.4**，未发生冲突 ✅

### 🔴 P0-4　seckill-service 的 jar 是"旧包"

**现象**：pom 里**明明有** `sentinel-datasource-nacos:1.8.8`，运行时却仍报同一个 `NacosDataSource` 找不到。

**根因（时间戳取证）**：

| 文件 | 修改时间 |
|---|---|
| `seckill-service/pom.xml` | **2026-09-23 15:48:27** |
| `seckill-service/target/seckill-service.jar` | 2026-09-23 15:41:34 |

**pom 比 jar 新 7 分钟** → 这个依赖是构建之后才加上去的，jar 里当然没有。
实测 `seckill-service.jar` 的 `BOOT-INF/lib/` 里确实**没有** `sentinel-datasource-nacos`。

**修复**：重新构建即可（本次的 `clean install` 已覆盖）。

> 教训：**改完 pom 一定要重新 `package`/`install`**，否则"我明明加了依赖"是最容易骗自己的假象。

### 🔴 P0-5　`nyw.jks` 只是改了文件名的旧 keystore

**现象**（user-service，最先炸在它这里）：
```
BeanCreationException: Error creating bean with name 'keyPair' ...
Caused by: java.lang.IllegalStateException: Cannot load keys from store: class path resource [nyw.jks]
Caused by: java.security.UnrecoverableKeyException: failed to decrypt safe contents entry:
    javax.crypto.BadPaddingException: Given final block not properly padded.
```

**根因取证**（`keytool -list` 实测）：

| | 实际值 | yaml 里写的 |
|---|---|---|
| 库类型 | **PKCS12** | — |
| storepass | **`${JKS_PASSWORD}`** | `${JKS_PASSWORD}` ❌ |
| alias | **`hmall`** | `nyw` ❌ |
| 文件 mtime | 2026-06-12（改名前的旧文件） | — |

即：**`hmall.jks` 被改名成 `nyw.jks`，但文件内容（密码、别名）一个都没跟着改。** yaml 在改名时已经改成 `${JKS_PASSWORD}`/`nyw` 了，两边对不上。

影响面：全项目只有 **gateway / nyw-service / user-service** 真正加载 keystore（都定义了 `JwtProperties` + `keyPair` 工厂），3 份 `nyw.jks` md5 完全相同。

**修复（生成新库，与 yaml 对齐）**：注意 yaml 注释里本来就写好了这条命令：

```bash
keytool -genkeypair -alias nyw -keyalg RSA -keysize 2048 -validity 3650 \
  -keypass ${JKS_PASSWORD} -keystore nyw.jks -storepass ${JKS_PASSWORD} \
  -dname "CN=nyw, OU=dev, O=nyw, L=SH, ST=SH, C=CN"
# 生成后同步覆盖三处：gateway / nyw-service / user-service 的 src/main/resources/nyw.jks
```

原始文件已备份为 `/tmp/nyw.jks.orig`（storepass `${JKS_PASSWORD}` / alias `hmall`）。

> **另一种改法**（不重新生成，只把 yaml 改回去）：
> `hm.jwt.alias: hmall`、`hm.jwt.password: ${JKS_PASSWORD}`。
> 两者选一即可，**关键是 alias / password / 文件内容三者必须自洽**。
